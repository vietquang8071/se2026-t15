   1 # Repository Guidelines
   2 
   3 ## Project Structure & Module Organization
   4 
   5 This repository contains the MVP workspace for **Meeting Minutes Assistant**, which turns meeting audio into structured minutes:
   6 
   7 - `apps/web/`: Next.js App Router frontend.
   8 - `apps/api/`: NestJS API.
   9 - `packages/database/`: Prisma schema and shared PostgreSQL client.
  10 - `docker-compose.yml`: local PostgreSQL service.
  11 - `docs/`: product scope, output schemas, and feature breakdown.
  12 
  13 ## Build, Test, and Development Commands
  14 
  15 Install with `pnpm install`, copy `.env.example` to `.env`, then start PostgreSQL with `docker compose up -d`. Useful commands:
  16 
  17 - `pnpm dev`: start Next.js and NestJS through Turborepo.
  18 - `pnpm build`, `pnpm lint`, `pnpm typecheck`: build and check workspace packages.
  19 - `pnpm db:generate`, `pnpm db:migrate`, `pnpm db:studio`: manage Prisma Client and the development database.
  20 
  21 Document setup changes in `README.md` and keep root scripts coordinated with Turborepo tasks.
  22 
  23 ## Coding Style & Naming Conventions
  24 
  25 Use TypeScript and two-space indentation. Name React components and Nest classes in PascalCase, Nest providers with role suffixes (`PrismaService`), and utility functions in camelCase. Use descriptive, lowercase, hyphen-separated Markdown filenames. Keep headings hierarchical, indent nested list items consistently, and label fenced code blocks. Prefer repository-relative links over machine-specific paths.
  26 
  27 Preserve established schema names such as `anchor_date` and `source_timestamp`, ISO dates (`YYYY-MM-DD`), and identifiers such as `ACT-001`. Use ESLint and the workspace Prettier scripts for linting and formatting.
  28 
  29 ## Testing Guidelines
  30 
  31 There is no shared test suite or coverage threshold yet. When adding product behavior, add tests in the owning app and document its test command. For documentation changes, inspect tables and Mermaid diagrams, check links, and validate JSON examples. Cross-check scope and schemas between both product documents, and verify calendar calculations in temporal-resolution examples.
  32 
  33 ## Commit & Pull Request Guidelines
  34 
  35 The short Git history uses messages such as `add: document about product description and feature overview` and `update README`; no strict convention is established. Write concise, descriptive commit subjects and keep changes focused.
  36 
  37 In pull requests, explain what changed and why, reference affected feature cards or issues when available, and state validation performed. Include screenshots when rendered layout changes need visual review.
  38 
  39 ## Security & Configuration
  40 
  41 Keep API keys, credentials, private recordings, and identifiable transcripts out of commits. Use synthetic meeting examples in documentation and future test fixtures.

  16 ## 1. Branch Strategy
  17 
  18 We use a simplified Git Flow: `develop` collects reviewed work, while `main` holds stable, release-ready code. Short-lived work branches keep changes isolated until review.
  19 
  20 If `develop` does not yet exist, the repository owner creates it once from `main` in GitHub before contributors begin work.
  21 
  22 | Branch | Purpose | Base branch |
  23 | --- | --- | --- |
  24 | `main` | Stable, release-ready code | — |
  25 | `develop` | Main integration branch for the next release | `main` when first created |
  26 | `feature/*` | New functionality | `develop` |
  27 | `fix/*` | Bug fixes outside a production hotfix | `develop` |
  28 | `docs/*` | Documentation changes | `develop` |
  29 | `refactor/*` | Code restructuring without intended behavior changes | `develop` |
  30 | `hotfix/*` | Critical fixes to code already released from `main` | `main` |
  31 
  32 ```mermaid
  33 flowchart LR
  34     M["main: stable releases"] -->|create once during setup| D["develop: integration"]
  35     D -->|branch| W["feature/*, fix/*, docs/*, refactor/*"]
  36     W -->|reviewed PR; squash merge| D
  37     D -->|release PR; merge commit| M
  38     M -->|branch for critical fix| H["hotfix/*"]
  39     H -->|reviewed PR| M
  40     M -->|PR after hotfix; synchronize| D
  41 ```
  42 
  43 - `main` **MUST** contain stable, release-ready code. `develop` **MUST** be the main integration branch.
  44 - Developers **MUST NOT** push directly to `main` or `develop`. Every change to either branch **MUST** arrive through a PR.
  45 - `feature/*`, `fix/*`, `docs/*`, and `refactor/*` branches **MUST** start from and target `develop`.
  46 - `hotfix/*` branches **MUST** start from `main`. A reviewed hotfix **MUST** be merged into `main`, then synchronized back into `develop` through a PR from `main` to `develop` so the fix remains in future releases.
  47 - MVP releases **MUST** use a PR from `develop` into `main`. Release branches are not required for the initial MVP.
  48 
  49 Traditional Git Flow adds long-lived release branches. For a three-person MVP, direct release PRs from `develop` provide a review point without another branch to maintain. Reserve `hotfix/*` for urgent problems in the released version; routine bugs belong on `fix/*`.
  50 
  51 ## 2. Branch Naming Convention
  52 
  53 Name branches `<type>/<issue-id>-<short-description>` when a related GitHub Issue exists. If there is no Issue, use `<type>/<short-description>`; never invent an Issue number. The `issue-id` is the numeric GitHub Issue number, and the description briefly identifies the task.
  54 
  55 | Type | Use for |
  56 | --- | --- |
  57 | `feature` | New user-facing or internal functionality |
  58 | `fix` | Non-production bug fixes |
  59 | `docs` | Documentation changes |
  60 | `refactor` | Code restructuring without intended behavior changes |
  61 | `hotfix` | Critical production fixes |
  62 
  63 Use lowercase English letters for words, digits for Issue numbers, and `kebab-case` for descriptions. Branch names **MUST NOT** contain spaces or unnecessary special characters. Keep names short, meaningful, and descriptive; use only the types above. Each branch **SHOULD** address one Issue or independent task, and unrelated tasks **MUST NOT** be combined. An existing related Issue number **MUST** appear in the branch name. Generic names such as `feature/test`, `fix/bug`, and `my-branch` are not acceptable.
  64 
  65 Valid examples:
  66 
  67 ```text
  68 feature/12-audio-upload
  69 feature/13-whisper-transcription
  70 feature/14-speaker-diarization
  71 feature/15-meeting-summary
  72 fix/21-incorrect-timestamp
  73 fix/22-audio-validation
  74 hotfix/30-upload-service-error
  75 docs/31-update-readme
  76 refactor/32-extraction-service
  77 docs/update-contributing
  78 ```
  79 
  80 | Invalid name | Why it violates the convention |
  81 | --- | --- |
  82 | `Feature/12-Audio-Upload` | Words and type must be lowercase. |
  83 | `feature/12_audio_upload` | The description must use hyphens, and an Issue number must be separated from it by a hyphen. |
  84 | `feature/12-audio upload` | Spaces are not allowed. |
  85 | `feature/test` | The description does not identify a meaningful task. |
  86 | `fix/bug` | The description is too generic. |
  87 | `my-branch` | It lacks a supported type and a descriptive name. |
  88 
  89 ## 3. Commit Convention
  90 
  91 Use [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/). The format is `<type>(<scope>): <description>`, or `<type>: <description>` when the scope is omitted. A scope names the affected area, such as `audio`, `transcription`, or `extraction`.
  92 
  93 | Commit type | Use for |
  94 | --- | --- |
  95 | `feat` | New features |
  96 | `fix` | Bug fixes |
  97 | `docs` | Documentation changes |
  98 | `refactor` | Code restructuring without behavior changes |
  99 | `test` | Added or modified tests |
 100 | `chore` | Maintenance and configuration changes |
 101 | `perf` | Performance improvements |
 102 | `ci` | CI/CD changes |
 103 
 104 Commit messages **MUST** be in English and use lowercase types and scopes. Descriptions **MUST** be concise and meaningful, and **SHOULD** start with an imperative verb. Use the type that describes the change: feature work on `feature/*` uses `feat`, while a hotfix on `hotfix/*` generally uses `fix`. Branch types and commit types are distinct; supporting test or documentation commits can use `test` or `docs` on a feature branch. Each commit **SHOULD** contain one logical change. Do not use vague descriptions such as `update`, `fix bug`, `done`, or `final`.
 105 
 106 Valid examples:
 107 
 108 ```text
 109 feat(audio): implement audio upload
 110 feat(transcription): integrate whisper api
 111 feat(diarization): add speaker labeling
 112 feat(extraction): generate meeting summary
 113 fix(transcript): correct segment timestamps
 114 fix(temporal): resolve relative dates
 115 docs: update contribution guidelines
 116 refactor(extraction): simplify processing pipeline
 117 test(audio): add upload validation tests
 118 ```
 119 
 120 | Invalid message | Why it violates the convention |
 121 | --- | --- |
 122 | `feature(audio): implement audio upload` | `feature` is a branch type; the commit type is `feat`. |
 123 | `Feat(Audio): Implement audio upload` | The type and scope must be lowercase. |
 124 | `fix bug` | It lacks the required type separator and gives no useful detail. |
 125 | `done` | It has no type and does not describe a change. |
 126 
 127 For an incompatible change, append `!` after the type or scope and explain the impact in a `BREAKING CHANGE:` footer. For example:
 128 
 129 ```text
 130 feat(api)!: change transcript response format
 131 
 132 BREAKING CHANGE: clients must read segments from the transcript object.
 133 ```

 135 ## 4. Development Workflow
 136 
 137 For a new audio upload feature, follow these steps. Start with a clean working tree so switching branches does not mix unrelated work.
 138 
 139 1. Switch to the local integration branch:
 140 
 141    ```bash
 142    git switch develop
 143    ```
 144 
 145 2. Update local `develop` from the remote. `--ff-only` avoids creating an accidental merge commit:
 146 
 147    ```bash
 148    git pull --ff-only origin develop
 149    ```
 150 
 151 3. Create the feature branch from the updated `develop`:
 152 
 153    ```bash
 154    git switch -c feature/12-audio-upload
 155    ```
 156 
 157 4. Implement the feature and run relevant tests.
 158 
 159 5. Review local changes before staging:
 160 
 161    ```bash
 162    git status
 163    git diff
 164    ```
 165 
 166 6. Stage and commit the logical change:
 167 
 168    ```bash
 169    git add .
 170    git diff --cached
 171    git commit -m "feat(audio): implement audio upload"
 172    ```
 173 
 174    Developers **SHOULD** inspect staged changes before committing and avoid staging unrelated files or secrets. If `git add .` stages too much, unstage the unwanted paths and stage only the intended files.
 175 
 176 7. Push the feature branch:
 177 
 178    ```bash
 179    git push -u origin feature/12-audio-upload
 180    ```
 181 
 182 8. Create a PR from `feature/12-audio-upload` into `develop`.
 183 
 184 9. If reviewers request changes, continue on the same feature branch, commit the corrections, and push new commits. Address feedback in the existing PR; do not open another PR for the same task.
 185 
 186 10. Once the PR is merged, update local `develop`:
 187 
 188     ```bash
 189     git switch develop
 190     git pull --ff-only origin develop
 191     ```
 192 
 193 Step 2 updates the local `develop` branch. If work is still in progress and `develop` receives new commits, integrate its latest remote state **into the existing feature branch** instead:
 194 
 195 ```bash
 196 git switch feature/12-audio-upload
 197 git fetch origin
 198 git merge origin/develop
 199 ```
 200 
 201 Resolve any conflicts, run relevant tests, and push the branch. This merge-based approach preserves shared branch history and does not require a force push.

 203 ## 5. Pull Request Rules
 204 
 205 | Source branch | Target branch | Purpose |
 206 | --- | --- | --- |
 207 | `feature/*` | `develop` | New feature |
 208 | `fix/*` | `develop` | Routine bug fix |
 209 | `docs/*` | `develop` | Documentation |
 210 | `refactor/*` | `develop` | Refactoring |
 211 | `develop` | `main` | MVP release |
 212 | `hotfix/*` | `main` | Critical released-code fix |
 213 | `main` | `develop` | Synchronize a merged hotfix |
 214 
 215 Feature branches **MUST NOT** target `main` directly. Each PR **SHOULD** cover one task or Issue, and unrelated functionality **MUST NOT** be combined. PR titles **SHOULD** follow Conventional Commits when appropriate. PR descriptions **MUST** explain what changed and why, link a related Issue when applicable, and include testing instructions or evidence. UI changes **SHOULD** include screenshots when useful. AI pipeline changes **SHOULD** include relevant sample inputs and outputs when possible, with confidential information removed.
 216 
 217 Draft PRs **MAY** be used for incomplete work, but **MUST NOT** be merged until marked ready and reviewed. Address requested changes in the same PR.
 218 
 219 To open a PR in GitHub: **Repository → Pull requests → New pull request → select the base and compare branches → Create pull request**. Confirm the base and compare branches before submitting.
 220 
 221 Example PR for `feature/12-audio-upload`:
 222 
 223 | Field | Example |
 224 | --- | --- |
 225 | Base / compare | `develop` / `feature/12-audio-upload` |
 226 | Title | `feat(audio): implement audio upload` |
 227 | Why | Allow users to provide a meeting recording for transcription. |
 228 | Changes | Add the upload flow and validate the selected audio file. |
 229 | Issue | Related to #12. |
 230 | Testing | Ran relevant automated tests; manually checked a valid upload and invalid-file feedback. |

 232 ## 6. Code Review Rules
 233 
 234 With three developers, every PR **MUST** receive at least one approval from another team member before merging. Authors **MUST NOT** approve their own PRs. Important unresolved review comments **MUST** be addressed, unresolved merge conflicts **MUST** be cleared, and all required CI checks **MUST** pass if CI is configured. If CI is not configured, the author **MUST** manually perform relevant tests and document the results in the PR.
 235 
 236 Changes targeting `main` **MUST** be approved as part of a team-agreed release, including urgent hotfixes. Reviewers **SHOULD** give constructive, actionable feedback and check:
 237 
 238 - [ ] Does the change do what the PR and Issue describe?
 239 - [ ] Is it understandable and maintainable?
 240 - [ ] Are behavior and interfaces compatible with related work?
 241 - [ ] Were relevant tests run, and are the results documented?
 242 - [ ] Are there security or data-handling concerns, such as exposed secrets or sensitive meeting content?
 243 
 244 GitHub review outcomes have different meanings:
 245 
 246 | Outcome | Meaning |
 247 | --- | --- |
 248 | **Approve** | The changes meet the review requirements. |
 249 | **Request changes** | Important issues must be resolved before approval. |
 250 | **Comment** | Feedback or discussion without approval or a formal request for changes. |
 251 
 252 These rules apply even if the repository has not yet been configured to enforce them automatically.

 254 ## 7. Merge Strategy
 255 
 256 Use **Squash and Merge** for `feature/*`, `fix/*`, `docs/*`, and `refactor/*` PRs into `develop`. It leaves one integration commit per completed task, reduces noise from intermediate commits, and makes finished work easier to find. Check that the squash commit message follows the commit convention.
 257 
 258 For a release PR from `develop` to `main`, prefer a **regular merge commit** to preserve the relationship between the integration and release branches. Merge hotfix PRs into `main` after review, then use a PR from `main` into `develop` to carry the fix forward. A regular merge commit is appropriate for this synchronization so both branches retain the hotfix ancestry.
 259 
 260 Do not merge PRs with unresolved conflicts. Do not rewrite the history of protected branches or force push to `main` or `develop`. After resolving conflicts, rerun relevant tests and keep the resulting Git history understandable.
 261 
 262 For example, if `feature/12-audio-upload` conflicts with new work on `develop`, resolve it on the feature branch:
 263 
 264 ```bash
 265 git switch feature/12-audio-upload
 266 git fetch origin
 267 git merge origin/develop
 268 git status
 269 git diff --name-only --diff-filter=U
 270 ```
 271 
 272 Git reports the conflicted files. Open each file, choose the intended combined content, and remove the conflict markers (`<<<<<<<`, `=======`, `>>>>>>>`). Then stage each resolved file and finish the merge:
 273 
 274 ```bash
 275 git add path/to/resolved-file
 276 git merge --continue
 277 ```
 278 
 279 Run the relevant tests for the affected code, document the result in the PR, and push the updated branch:
 280 
 281 ```bash
 282 git push origin feature/12-audio-upload
 283 ```
 284 
 285 Repeat the resolution for every conflicted file before `git merge --continue`. Do not push the branch until the merge is complete and tests have passed.
 286 
 287 ## 8. Branch Cleanup
 288 
 289 Completed work branches **SHOULD** be deleted after their PRs merge. The repository owner **SHOULD** enable GitHub's **Automatically delete head branches** option when appropriate. Before enabling it, protect `main` and `develop` against deletion: each can be the head branch of a PR in this workflow. After a merge, update local `develop` and remove obsolete local branches:
 290 
 291 ```bash
 292 git switch develop
 293 git pull --ff-only origin develop
 294 git branch -d feature/12-audio-upload
 295 ```
 296 
 297 `git branch -d` deletes only the local branch and refuses if Git cannot confirm it was merged. After **Squash and Merge**, Git may still consider the original feature branch unmerged because its individual commits were replaced by a squash commit. Only after verifying that the PR merged successfully and its intended changes are present in `develop`, use:
 298 
 299 ```bash
 300 git branch -D feature/12-audio-upload
 301 ```
 302 
 303 If the remote branch remains and is no longer needed, delete it with:
 304 
 305 ```bash
 306 git push origin --delete feature/12-audio-upload
 307 ```
 308 
 309 The `git branch` commands affect only your local repository; `git push origin --delete` removes the branch from GitHub for everyone. Developers **MUST NOT** delete `main` or `develop`, or any branch that contains unfinished or unmerged work.

 129 ## 3. Internal processing pipeline
 130 
 131 Pipeline phải chạy theo thứ tự trong bảng. Mỗi bước nhận model nội bộ có kiểu rõ, trả output có thể kiểm tra; lỗi provider/output được đổi sang error envelope trong [contract](./llm-service-contract.md#8-error-contract).
 132 
 133 | Bước/component | Trách nhiệm | Input → Output | Dependencies | Error handling | Unit/contract tests |
 134 |---|---|---|---|---|---|
 135 | 1. RequestValidator | Xác thực bearer token, contract version, field, enum, IDs, date/timezone, segment ordering/duration và payload limit. | JSON body → typed request hoặc validation errors. | FastAPI, Pydantic v2, config. | Input sai trả 400; body quá lớn trả 413; transcript rỗng trả 422. Chưa gọi provider. | Field thiếu/sai, unknown field, duplicate IDs, overlap hợp lệ, segment sai bounds, timezone sai, auth. |
 136 | 2. TranscriptContextBuilder | Tạo segment map, participant/speaker map đã xác nhận, compact context và token estimate; giữ nguyên source IDs/text. | Typed request → extraction context + source index. | Request schemas, tokenizer/provider capability nếu có. | Không âm thầm cắt text; vượt budget chuyển TranscriptTooLong hoặc trả window plan. | Giữ nguyên text/IDs, mapping speaker, duration, token boundary và segment order. |
 137 | 3. ExtractionService + PromptRegistry | Chọn prompt theo version/ngôn ngữ/modules; gọi một lần extraction có structured schema. | Context + module set → candidate JSON. | LLMProvider, prompt templates. | Timeout/rate-limit/provider failure được chuẩn hóa; raw response không ghi log. | Fake provider cho từng module set, prompt version, vi/en, timeout và invalid JSON. |
 138 | 4. TemporalResolver | Parse raw temporal expressions và tính exact date/range/unresolved từ anchor/timezone. | Candidate raw phrases + anchor_date, timezone → TemporalResolution. | Python date/calendar/timezone standard library. | Phrase không đủ rõ giữ unresolved; ngày không hợp lệ không tự sửa. | Weekdays, tuần, cuối tháng, leap year, qua tháng/năm, timezone, mơ hồ. |
 139 | 5. EvidenceVerifier | Kiểm tra source IDs, cùng request/revision, timestamp projection và semantic support của claim. | Candidate claims + source index → verified/review/drop decision. | Source index và verifier prompt/provider đã cấu hình. | Unsupported claim bị bỏ/đánh review; module không còn nội dung dùng được trả UNVERIFIED_EVIDENCE. | ID hợp lệ/sai, segment sai meeting/revision, quote không support, mâu thuẫn, empty evidence. |
 140 | 6. OutputValidator | Validate Pydantic schema, module semantics, null/empty rules, temporal invariants, IDs, needs_review và source subsets. | Candidate đã resolve/verify → validated response modules. | Request/response schemas. | Sau tối đa một structured repair, output còn invalid trả INVALID_STRUCTURED_OUTPUT; không trả partial success. | JSON invalid, field thiếu, enum sai, date state không nhất quán, requested module null. |
 141 | 7. ResponseBuilder | Copy metadata đã biết, gán response-local IDs, tính source_timestamp, điền null cho module chưa yêu cầu, thêm processing metadata. | Validated modules + request + provider metadata → response JSON. | Schemas, source index, request context. | Lỗi nội bộ trả INTERNAL_ERROR, không serialize stack trace. | Echo request/revision, thứ tự IDs, timestamp từ segment start, token usage optional. |

 143 ### 3.1 Chi tiết luồng dữ liệu
 144 
 145 1. Web gửi immutable transcript.revision_id; request validator từ chối revision thiếu segments dùng được trước khi tiêu tốn provider call.
 146 2. Context builder lập index segment_id → {start, end, speaker_id, text}. Speaker ID chỉ được đổi sang tên participant nếu request đã có mapping.
 147 3. Prompt nhận context và transcript dưới dạng data block JSON đã serialize, tách khỏi system instructions. Model trả candidate modules, raw temporal phrases và source IDs; model không được tự tạo source timestamps hoặc persistent IDs.
 148 4. Temporal resolver dùng anchor/timezone tính date state cho Action Items, Follow-ups và Timeline Events. Cùng một expression dùng cùng hàm resolve, không tính riêng trong từng prompt.
 149 5. Evidence verifier kiểm tra source reference và mức hỗ trợ ngữ nghĩa. Kết quả uncertain được đánh review hoặc loại bỏ; bằng chứng cấu trúc hợp lệ không tự chứng minh claim đúng.
 150 6. Output validator kiểm tra invariants cuối. Requested module không thể null trong response thành công; list rỗng sau extraction hợp lệ là [].
 151 7. Response builder echo meeting/revision/request IDs, sắp xếp artifact theo quy tắc module trong contract, gán ID hiển thị theo thứ tự trả về và tính source_timestamp từ segment gốc. Web persist response, không phải LLM Service.

 153 ## 4. LLM extraction design
 154 
 155 ### 4.1 Prompt templates và versioning
 156 
 157 - Lưu prompt templates như file versioned trong app/prompts/v1/; không nhúng prompt dài trong route handler.
 158 - System instructions xác định role, output language, sáu module, business boundaries, cấm bịa, schema và source citation requirements.
 159 - User prompt chứa meeting metadata cần cho extraction và transcript segments dưới dạng data block JSON. Không nối transcript thành phần system/developer instruction.
 160 - Transcript là untrusted data: câu nói như “bỏ qua hướng dẫn trước” chỉ là nội dung cuộc họp. Prompt phải nói rõ không nhận chỉ thị trong transcript để đổi role, schema, policy hoặc tool use.
 161 - prompt_version được trả trong response; mọi sửa đổi làm thay đổi cách trích xuất tăng version để evaluation có thể so sánh.
 162 - Chỉ đưa vào prompt dữ liệu cần thiết. Không gửi meeting IDs có ý nghĩa cá nhân, credentials hay nội dung không thuộc transcript.
 163 - Yêu cầu structured output theo schema Pydantic/JSON Schema khi provider hỗ trợ. Nếu provider chỉ trả text, parse JSON nghiêm ngặt rồi validate; chỉ cho một lần repair có giới hạn.
 164 - Repair prompt nhận lỗi schema đã rút gọn và candidate output dưới dạng untrusted data; không đưa stack trace hoặc secrets vào prompt.
 165 - Không yêu cầu hoặc lưu chain-of-thought. Chỉ nhận artifact, source IDs và các field cần thiết.
 166 
 167 ### 4.2 Provider abstraction
 168 
 169 Một interface nhỏ LLMProvider tách ExtractionService khỏi SDK cụ thể. Interface tối thiểu cần:
 170 
 171 - generate_structured(messages, schema, model_config, timeout): trả payload đã decode, model_id, token usage nếu provider cung cấp.
 172 - count_tokens(text, model_config) hoặc khả năng ước lượng token/context để preflight và lập window.
 173 - Chuẩn hóa lỗi thành nhóm timeout, rate-limit, authentication/configuration, transient provider failure, permanent provider failure và malformed output.
 174 - Không làm lộ provider-specific request/response trong HTTP contract.
 175 
 176 MVP chỉ cần một adapter thật sau khi nhóm chọn provider/model và một fake adapter cho tests. Không tạo registry/plugin framework hoặc nhiều adapter chưa có use case. provider và model_id thật được ghi trong processing metadata; fixtures dùng tên giả lập.
 177 
 178 ### 4.3 Lựa chọn extraction pass
 179 
 180 | Phương án | Latency/cost | Accuracy/maintainability | Đánh giá |
 181 |---|---|---|---|
 182 | Single-pass: một structured generation cho tất cả requested modules | Thấp nhất; ít round trip. | Tốt cho schema thống nhất nhưng prompt dài, nhầm ranh giới module và source checking yếu hơn. | Phù hợp P03 Summary/Actions và transcript ngắn; cần validation/evidence stage trước khi coi full result đã kiểm chứng. |
 183 | Multi-stage theo chủ đề rồi hợp nhất | Cao hơn; nhiều lần gọi và nhiều bước state cần debug. | Có thể dùng ngữ cảnh/verification riêng nhưng merge có thể tạo duplicate hoặc làm mất source. | Chưa cần framework riêng cho MVP; dùng sau benchmark nếu single-pass hụt chất lượng. |
 184 | Một lần gọi riêng cho từng module | Latency/cost cao nhất, lỗi một module dễ cô lập hơn. | Prompt đơn giản hơn nhưng các module có thể mâu thuẫn về owner/date và lặp claim. | Không khuyến nghị làm mặc định. |
 185 
 186 **Đề xuất MVP:** một generation pass cho các module được yêu cầu trong mỗi transcript window; sau đó deterministic temporal resolution, structural/reference validation và một evidence-verification pass theo batch cho claims cần kiểm tra. Nếu output schema sai, tối đa một repair attempt. Đây không phải multi-agent architecture; verifier chỉ trả trạng thái support/uncertain/unsupported, không tự tạo artifact mới. Đo chi phí và latency trên gold dataset trước khi bỏ verifier hoặc chuyển sang pipeline nhiều lượt.
 187 
 188 Trong P03, có thể bắt đầu với Summary + Actions và fake provider/fixtures, sau đó tích hợp provider thật theo M1. P07 thêm bốn module còn lại, kiểm tra phân loại nghiệp vụ và evidence trước M2.
 189 
 190 ### 4.4 Sáu module, tiếng Việt/Anh và mâu thuẫn
 191 
 192 - Một schema response giữ sáu key cố định; requested_modules quyết định module nào chạy, giúp P03 chỉ dùng Summary/Actions và P07 mở rộng mà không đổi root response shape.
 193 - output_language là vi hoặc en; transcript vẫn giữ transcript.language gốc. Không dịch raw statement/source text.
 194 - Tên riêng, display name và speaker labels giữ nguyên theo request/transcript. Không tự chuẩn hóa hai tên thành một người.
 195 - Action Item yêu cầu task/deliverable cụ thể. Owner có thể null nếu có candidate nhưng chưa xác nhận; đánh needs_review, không trình bày như đã giao việc.
 196 - Decision chỉ được tạo khi có câu chốt/consensus; proposal và opinion không đủ. Rationale/alternatives null nếu không được nêu.
 197 - Open Issue là câu hỏi/bất đồng chưa giải; Follow-up là bước cụ thể để quay lại/kiểm tra. Một cuộc trao đổi có thể tạo cả hai nếu source chứng minh hai nội dung riêng.
 198 - Khi transcript mâu thuẫn, giữ claim và evidence riêng, không tự chọn người “đúng”. Nếu mâu thuẫn chưa được giải, không phát hành decision đã chốt; tạo issue/review item phù hợp.
 199 - Summary tổng hợp nội dung nhưng mỗi topic và overview vẫn phải có source IDs; không phát biểu kết luận không có trong cuộc họp.
 200 - Priority/severity chỉ được điền khi được nói rõ hoặc có rubric đã được nhóm chốt; nếu không, null.

 202 ## 5. Temporal resolution engine
 203 
 204 ### 5.1 Hybrid approach
 205 
 206 LLM nhận diện temporal phrase, target event/task và segment evidence. Python TemporalResolver parse phrase, áp quy tắc lịch trên meeting.anchor_date và meeting.timezone, rồi trả exact_date, date_range hoặc unresolved theo contract. LLM không thực hiện phép tính calendar cuối.
 207 
 208 ### 5.2 Quy trình resolve
 209 
 210 1. Thu thập phrase nguyên văn từ các candidate Action Items, Follow-ups và Timeline Events.
 211 2. Chuẩn hóa khoảng trắng để phân tích nhưng giữ nguyên raw phrase.
 212 3. Xác định loại expression: ngày ISO/cụ thể, weekday tương đối, tuần, cuối tháng, khoảng ngày hoặc thiếu ngữ cảnh.
 213 4. Chuyển anchor date sang local civil date theo timezone của meeting; không gọi system clock để chọn ngày.
 214 5. Tính kết quả bằng datetime.date, calendar.monthrange và quy tắc ISO week; không cộng trừ 24-hour duration để thay thế calendar arithmetic.
 215 6. Nếu expression chỉ cho biết range, giữ hai đầu inclusive; không chọn một ngày đại diện.
 216 7. Nếu nhiều cách diễn giải hợp lý, trả unresolved và cần review.
 217 8. Ghi cùng resolution vào các module có cùng temporal expression để deadline và event không lệch nhau.
 218 
 219 ### 5.3 Chính sách lịch v1 đề xuất
 220 
 221 | Trường hợp | Xử lý |
 222 |---|---|
 223 | “Thứ Sáu này” | Ngày thứ Sáu đầu tiên từ anchor date trở đi; anchor vào thứ Sáu thì dùng chính ngày đó. 2026-10-05 → 2026-10-09. |
 224 | “Tuần sau” | ISO week kế tiếp, thứ Hai–Chủ nhật inclusive. 2026-10-05 → 2026-10-12 đến 2026-10-18; exact day chưa biết nên không suy ra thứ Hai. |
 225 | “Cuối tháng” | Ngày cuối tháng chứa anchor date; với 2026-10-05 là 2026-10-31. Đây là policy đề xuất khớp ví dụ gốc, cần P08-01 xác nhận. |
 226 | “Cuối tháng sau” | Ngày cuối tháng kế tiếp anchor month; kiểm tra chuyển năm và số ngày tháng bằng thư viện lịch. |
 227 | “Ngày 12” không rõ tháng/năm | Resolve khi transcript cho một tháng/năm duy nhất; nếu không, unresolved. |
 228 | Ngày qua tháng/năm hoặc năm nhuận | Dùng phép tính calendar; không dựa vào số ngày cố định trong tháng. |
 229 | Timezone | Dùng IANA timezone của meeting để xác định ngày dân sự. Timestamp transcript vẫn là elapsed seconds trên audio gốc. |
 230 | Mơ hồ/mâu thuẫn | Giữ raw phrase, các source IDs và status unresolved; needs_review là true. |
 231 
 232 Các ví dụ này sửa cách diễn giải temporal sai trong Product Description/Feature Overview; xem Open Questions. UI phải hiển thị date range/unresolved riêng, không sắp xếp chúng thành một due date giả.

 234 ## 6. Chiến lược transcript dài
 235 
 236 ### 6.1 Token budgeting
 237 
 238 - Byte limit HTTP được kiểm tra trước khi parse toàn bộ request vào model; giới hạn deployment phải được công bố.
 239 - Adapter ước lượng token theo model/provider đang cấu hình. Budget dành riêng chỗ cho system prompt, meeting context, output schema, completion và safety margin.
 240 - Dùng model context window từ cấu hình adapter; không assume một con số chung cho mọi provider.
 241 - Nếu request vượt token budget một pass nhưng còn trong hard limit, chia cửa sổ theo ranh giới segment. Không cắt giữa segment hoặc bỏ segment có timestamp nếu nó là evidence cho overlap/turn-taking.
 242 - Nếu không thể xử lý hết cửa sổ trong total request budget hoặc hard limit, trả TRANSCRIPT_TOO_LONG; không trả partial success.
 243 
 244 ### 6.2 MVP windowing
 245 
 246 1. Ưu tiên single-pass cho transcript vừa context.
 247 2. Với transcript dài, tạo windows theo thứ tự thời gian và dừng trước token limit; overlap chỉ thêm trọn segment boundary cần thiết, có giới hạn cấu hình.
 248 3. Giữ global segment_id, start/end và speaker ID trong từng window; không đổi ID/offset.
 249 4. Trích candidate artifacts theo cửa sổ; mỗi item giữ source IDs.
 250 5. Gộp candidate trùng dựa trên source ID overlap, semantic content và evidence verifier; không chỉ so sánh string giống nhau.
 251 6. Gộp source IDs theo thời gian và gán response IDs sau khi deduplicate.
 252 7. Tạo global summary từ các topic/window summaries có evidence, không nối máy móc các summary riêng.
 253 8. Resolve temporal sau khi merge để mọi candidate dùng cùng anchor date/timezone.
 254 9. Với candidate cùng chủ đề nhưng statement mâu thuẫn giữa windows, giữ cả evidence và yêu cầu review; không loại một phía theo thứ tự xử lý.
 255 
 256 ### 6.3 Phạm vi MVP và cải tiến
 257 
 258 **Tối thiểu cho MVP:** token preflight, single-pass trong context, segment-aligned windows khi cần, overlap giới hạn, deterministic merge, dedup có source refs, global summary có evidence và lỗi có cấu trúc nếu vượt hard limit. Kiểm tra transcript được stitch từ Audio Processing Service bằng fixtures trước khi tích hợp.
 259 
 260 **Sau benchmark/Post-MVP:** adaptive window size theo topic, map-reduce nhiều tầng, semantic clustering chuyên biệt, incremental re-extraction theo transcript delta, retrieval index và distributed workers. Không thêm vector database, queue hoặc orchestration framework để xử lý MVP.

 262 ## 7. Reliability và security
 263 
 264 ### 7.1 Reliability
 265 
 266 - Tất cả bước có request-level deadline; provider call bị cắt theo remaining request budget.
 267 - Provider adapter chuẩn hóa lỗi và không tự retry không giới hạn. Web Backend quản lý retry policy cho extraction job; đây là tầng duy nhất quyết định retry toàn HTTP request.
 268 - Structured-output repair tối đa một lần, chỉ cho lỗi format/schema có thể sửa; không dùng repair để biến thiếu evidence thành claim.
 269 - Failure ở bất kỳ module được yêu cầu nào làm request non-2xx; không ghi một response completed thiếu module.
 270 - LLM Service stateless; không tạo job, queue, DB hoặc deduplication store. Web dùng meeting/revision/module/config làm logical job key.
 271 - Giới hạn concurrency theo instance, trả 429 CAPACITY_LIMIT/Retry-After khi quá tải thay vì nhận request không giới hạn.
 272 - Provider/model/config có kiểm soát; lỗi credentials không được retry tự động.
 273 - Web Backend chỉ lưu artifact sau khi validate đúng meeting_id, transcript_revision_id, request_id và response contract.
 274 
 275 ### 7.2 Security và privacy
 276 
 277 - Transcript là untrusted user data, không phải instruction. JSON serialization và prompt boundary phải ngăn transcript ghi đè system instructions.
 278 - Không nhận audio/raw ASR payload; không ghi transcript, participant names, API keys, bearer tokens, full prompt hay raw provider response vào logs.
 279 - Logs chỉ lưu request/correlation ID, meeting ID nếu policy cho phép, revision ID, số segments/characters, duration, module set, provider/model/prompt version, token counts, latency và error code.
 280 - Không log evidence snippets; nếu debug cần text, chỉ bật trong môi trường synthetic có thời hạn và quyền truy cập hạn chế.
 281 - Không persist transcript tại LLM Service; dữ liệu trong memory chỉ tồn tại trong thời gian xử lý, cần được giải phóng sau response/failure.
 282 - Chỉ Web Backend được gọi endpoint extraction bằng token riêng; token từ secret manager, rotate được và không commit vào repo.
 283 - Không gắn role/user claims vào transcript; authentication nội bộ xác thực caller service, còn Web chịu trách nhiệm authorization meeting.
 284 - Production egress chỉ tới provider được phê duyệt; đánh giá retention, data region, encryption và provider logging trước khi gửi transcript thật.
 285 - Error envelope không trả stack trace, SQL, đường dẫn filesystem, quota details nhạy cảm hoặc nội dung transcript.
 286 - Logs và metrics tránh cardinality cao; không dùng raw request ID/meeting ID làm metric label.

 288 ## 8. Observability và evaluation
 289 
 290 ### 8.1 Structured logging và metrics
 291 
 292 Log JSON có request_id, transcript_revision_id, module set, provider/model, prompt_version, timestamp bắt đầu/kết thúc, latency từng stage, token usage khi provider có, số segments, số windows, số artifact, số artifact review, retry/error code và timeout budget còn lại. Không log transcript body hay prompt.
 293 
 294 Metrics đề xuất:
 295 
 296 - Request count theo status/error code/provider/model.
 297 - End-to-end latency và latency từng stage.
 298 - Provider timeout, rate-limit, malformed output, repair count, evidence rejection/review.
 299 - Input/output token usage và cost estimate theo bảng giá do nhóm cấu hình; không ghi giá/benchmark giả định trong tài liệu này.
 300 - Window count, transcript characters/segments và tỷ lệ vượt token budget.
 301 - Tỷ lệ item có needs_review, thiếu owner/deadline, temporal exact/range/unresolved.
 302 
 303 Correlation dùng request_id từ Web qua log của hai service; nếu truyền distributed trace trong tương lai thì dùng trace context chuẩn, không nhúng transcript trong span attributes.
 304 
 305 ### 8.2 Đánh giá extraction
 306 
 307 Chuẩn bị gold dataset từ transcript có quyền sử dụng, đã loại thông tin nhận diện không cần thiết. Mỗi sample có:
 308 
 309 - Transcript segments với speaker, timestamps và transcript revision.
 310 - Meeting context/anchor date/timezone.
 311 - Đáp án do người gán nhãn cho sáu modules, source segment IDs, owner/deadline, temporal state và mâu thuẫn.
 312 - Ghi chú trường hợp không có action/decision, owner không rõ, lời nói mơ hồ, nội dung Việt/Anh trộn và speaker chưa map.
 313 - Quy trình hai người gán nhãn cho subset và phân xử bất đồng; giữ provenance/consent của fixture.
 314 
 315 Tách dữ liệu tune prompt và regression; không dùng cùng một sample để vừa điều chỉnh prompt vừa tuyên bố kết quả holdout. Chạy evaluation cố định theo provider, model, prompt version, schema version và cấu hình temporal.
 316 
 317 | Metric | Cách tính |
 318 |---|---|
 319 | Precision/Recall/F1 theo artifact | Match item theo business definition và evidence; báo riêng từng module, không chỉ micro-average. |
 320 | Owner accuracy | So sánh owner đã xác nhận; tính riêng null/unassigned và role-based owner. |
 321 | Deadline accuracy | So sánh exact date, date range và unresolved state; sai status cũng tính là lỗi. |
 322 | Evidence grounding accuracy | Tỷ lệ claim có source segment đúng và ngữ nghĩa hỗ trợ; đo referential validity riêng với entailment. |
 323 | Hallucination rate | Claim không được source hỗ trợ trên tổng claim đã phát hành; phân loại bị drop, needs_review và lọt qua verifier. |
 324 | Temporal resolution accuracy | Exact date/range boundaries và needs_review so với gold; báo riêng ngày rõ và phrase mơ hồ. |
 325 | Empty-result behavior | Đo precision khi không có action/decision/follow-up/event; danh sách rỗng phải đúng khi transcript không chứa module đó. |
 326 | Contradiction handling | Đo decision sai do bỏ qua bất đồng và tỷ lệ issue/review được giữ lại khi hội thoại chưa chốt. |
 327 
 328 Không đặt benchmark results, target score hoặc quality threshold được phê duyệt khi nhóm chưa có baseline. P11-01/P11-05 ghi số liệu thực, model/config, dataset split, latency, số retry và giới hạn.

 376 ## 10. Implementation roadmap cho LLM Service
 377 
 378 Các task dưới đây là breakdown đề xuất nối với roadmap hiện tại, không đánh dấu trạng thái hoàn thành và không sửa implementation-roadmap.md. P00 là prerequisite quyết định provider, schema và data policy. Ưu tiên/cost là ước lượng thiết kế: P0 cần để bắt đầu integration, P1 cần cho M2/MVP, P2 là cải tiến benchmark-driven; complexity S/M/L tương ứng nhỏ/vừa/lớn.
 379 
 380 ### LLM-01 — Contract models và fixtures
 381 
 382 - **Objective:** Chuyển contract v1 thành Pydantic request/response/error models và fixtures dùng chung.
 383 - **Deliverables:** Request/response schemas cho sáu modules, error model, OpenAPI snapshots/fixtures, validation invariants và examples parse được.
 384 - **Dependencies:** P00-04; nhóm duyệt open questions làm thay đổi schema. Có thể bắt đầu trước khi Audio Processing Service/Web Backend hoàn tất.
 385 - **Affected components:** app/schemas/, tests/contract/, tests/fixtures/.
 386 - **Implementation approach:** extra='forbid', date/timezone parsing tường minh, module keys cố định, null/empty semantics đúng contract; không tạo DB model.
 387 - **Acceptance Criteria:** Full request/response, Summary+Actions subset, empty list, temporal states và error envelope pass schema; unknown field/version sai bị từ chối.
 388 - **Testing strategy:** Unit validation và contract tests offline; kiểm tra OpenAPI sinh từ FastAPI ở task runtime.
 389 - **Priority / complexity:** P0 / M.
 390 - **Roadmap mapping:** P00-04, P01-01, P07-01.
 391 
 392 ### LLM-02 — FastAPI runtime, health, auth và config
 393 
 394 - **Objective:** Tạo HTTP runtime riêng có thể chạy/deploy độc lập.
 395 - **Deliverables:** FastAPI app, GET /health, POST /v1/extractions skeleton, /openapi.json, bearer dependency, settings, Dockerfile và pyproject.toml.
 396 - **Dependencies:** LLM-01 cho response shape; không phụ thuộc API backend đã implement.
 397 - **Affected components:** app/main.py, app/api/, app/core/, Dockerfile, pyproject.toml.
 398 - **Implementation approach:** Dependency injection cho fake/real provider; route chỉ gọi service layer; health không gọi provider; không kết nối DB/queue.
 399 - **Acceptance Criteria:** Service khởi động Python 3.12+, auth đúng, OpenAPI phản ánh contract, health không lộ secrets và process dừng graceful.
 400 - **Testing strategy:** FastAPI TestClient với auth hợp lệ/sai, health/OpenAPI và error serialization.
 401 - **Priority / complexity:** P0 / M.
 402 - **Roadmap mapping:** Mở rộng P01-01 cho service mới; tích hợp setup tại P11-04.
 403 
 404 ### LLM-03 — Provider adapter và P03 Summary/Actions
 405 
 406 - **Objective:** Tạo structured extraction ban đầu cho Summary và Action Items.
 407 - **Deliverables:** LLMProvider protocol, adapter đầu tiên sau khi nhóm chọn provider, versioned prompt, Summary/Actions output và fake provider.
 408 - **Dependencies:** LLM-01/02; transcript fixtures đủ để làm trước ASR thật.
 409 - **Affected components:** app/providers/, app/prompts/v1/, app/services/extraction.py, schemas và integration tests.
 410 - **Implementation approach:** Một generation pass cho requested modules; metadata summary copy/tính từ request; owner/deadline không rõ giữ null/review; không chọn provider trong tài liệu này.
 411 - **Acceptance Criteria:** Summary + Actions response khớp schema/source IDs; lỗi provider map đúng envelope; P03-04 fixture pass trước khi provider thật được nghiệm thu.
 412 - **Testing strategy:** Fake provider cho deterministic tests; integration provider thật chỉ chạy bằng credential/dataset đã được nhóm duyệt, tách khỏi CI mặc định.
 413 - **Priority / complexity:** P0 / M.
 414 - **Roadmap mapping:** P03-04, refine tại P07-02, tích hợp end-to-end P03-06.
 415 
 416 ### LLM-04 — TemporalResolver
 417 
 418 - **Objective:** Resolve relative date trong Actions, Follow-ups và Timeline bằng quy tắc deterministic.
 419 - **Deliverables:** TemporalResolver, ba trạng thái date, raw phrase/evidence preservation và shared resolution output.
 420 - **Dependencies:** LLM-01 schema; có thể phát triển song song LLM-03 bằng calendar fixtures.
 421 - **Affected components:** app/schemas/temporal.py, app/services/temporal_resolver.py, tests/unit/.
 422 - **Implementation approach:** LLM chỉ nhận diện raw phrase; Python calendar rules nhận anchor_date và IANA timezone; không gọi system clock.
 423 - **Acceptance Criteria:** Ví dụ 2026-10-05 → Friday 2026-10-09, next week range 2026-10-12..2026-10-18, cuối tháng 2026-10-31; ambiguous giữ unresolved.
 424 - **Testing strategy:** Table-driven unit tests weekday boundaries, leap years, month/year rollover, invalid timezone và câu thiếu ngữ cảnh.
 425 - **Priority / complexity:** P1 / M.
 426 - **Roadmap mapping:** P08-01, P08-02, P08-04, đồng bộ persistence với P08-03.
 427 
 428 ### LLM-05 — Decision, Open Issues, Follow-ups và Timeline
 429 
 430 - **Objective:** Mở rộng extraction từ hai module đầu sang đủ sáu business modules.
 431 - **Deliverables:** Prompt/schema bốn module còn lại, ranh giới decision/proposal, issue/follow-up và timeline fields.
 432 - **Dependencies:** LLM-01/02/03; có thể làm song song LLM-04 trên fixtures nhưng integration dùng chung temporal model.
 433 - **Affected components:** app/prompts/, app/schemas/response.py, app/services/extraction.py, unit/integration fixtures.
 434 - **Implementation approach:** Giữ sáu response keys cố định; chỉ chạy modules yêu cầu; dùng IDs gán server-side; raw statements/source evidence luôn giữ.
 435 - **Acceptance Criteria:** Decision chỉ là lựa chọn đã chốt; open issue unresolved; follow-up khác task; timeline chỉ có event nói trong transcript; empty module trả [].
 436 - **Testing strategy:** Vietnamese/English fixtures có proposal, disagreement, no-item và overlapping module cases.
 437 - **Priority / complexity:** P1 / M.
 438 - **Roadmap mapping:** P07-01, P07-03, P07-04.
 439 
 440 ### LLM-06 — Evidence verifier và output validation
 441 
 442 - **Objective:** Không phát hành claim chỉ vì model trả segment ID tồn tại.
 443 - **Deliverables:** Source index validator, semantic verifier batch, needs_review/drop policy, timestamp derivation và bounded schema repair.
 444 - **Dependencies:** LLM-01/03/05; verifier có thể làm bằng fake fixture trước khi Web/Audio integration xong.
 445 - **Affected components:** app/services/evidence_verifier.py, output_validator.py, response.py, tests/contract.
 446 - **Implementation approach:** Deterministic kiểm tra IDs/same request/revision/subset/order/timestamp; verifier kiểm tra semantic support; một repair tối đa cho schema, không repair facts thiếu evidence.
 447 - **Acceptance Criteria:** Source ID sai bị từ chối; claim không được support bị review/drop; module không có output dùng được trả UNVERIFIED_EVIDENCE; không trả 200 partial.
 448 - **Testing strategy:** Positive/negative entailment fixtures, cross-revision ID, forged timestamp, missing owner/evidence và invalid review invariants.
 449 - **Priority / complexity:** P1 / L.
 450 - **Roadmap mapping:** P07-05 và P07-06.
 451 
 452 ### LLM-07 — Token budget và long-transcript windows
 453 
 454 - **Objective:** Xử lý transcript dài mà không làm mất segment/source alignment.
 455 - **Deliverables:** Token preflight, segment-aligned window builder, bounded overlap, artifact aggregation/dedup và global summary synthesis.
 456 - **Dependencies:** LLM-01/03/05; fixture transcript tự tạo đủ trước khi P05 audio chunking hoàn tất.
 457 - **Affected components:** app/services/context_builder.py, transcript_windows.py, extraction.py, tests/fixtures.
 458 - **Implementation approach:** Single pass khi vừa context; trên budget chia windows, giữ global segment IDs, merge rồi resolve temporal; vượt hard cap trả TRANSCRIPT_TOO_LONG.
 459 - **Acceptance Criteria:** Mọi segment được xử lý hoặc request fail rõ ràng; không mất source ID, không tạo item trùng tại overlap, giữ contradiction giữa windows.
 460 - **Testing strategy:** Synthetic windows ở ranh giới segment, duplicate overlap, dài hơn context và mâu thuẫn xuyên cửa sổ; không cần model thật cho merge mechanics.
 461 - **Priority / complexity:** P1 / L.
 462 - **Roadmap mapping:** Liên quan P05-01/P05-02/P05-06 về transcript gốc và P07-06 về extraction; đây là windowing văn bản phía LLM, không thay audio chunking.
 463 
 464 ### LLM-08 — Reliability, privacy và observability
 465 
 466 - **Objective:** Giới hạn lỗi, chi phí và dữ liệu nhạy cảm trong vận hành.
 467 - **Deliverables:** Request/provider deadlines, concurrency limit, error mapping, structured logs, latency/token metrics, secret handling và documented run config.
 468 - **Dependencies:** LLM-02/03; làm song song với extraction features.
 469 - **Affected components:** app/core/config.py, errors, provider adapter, API dependencies và deployment config.
 470 - **Implementation approach:** Retry toàn job do Web quyết định; không lưu transcript/log body; chỉ một structured repair; health tách khỏi provider.
 471 - **Acceptance Criteria:** Lỗi transient/permanent map đúng; capacity trả 429; không lộ secrets/transcript; per-request budget được enforce.
 472 - **Testing strategy:** Fake provider timeout/rate-limit/malformed response; log capture assertions; concurrency-limit tests.
 473 - **Priority / complexity:** P1 / M.
 474 - **Roadmap mapping:** P03-02 error handling, P05-04 retry boundaries, P11-04 reproducible setup.
 475 
 476 ### LLM-09 — Gold evaluation và acceptance
 477 
 478 - **Objective:** Đo chất lượng extraction thật mà không bịa benchmark hoặc dùng một demo để kết luận.
 479 - **Deliverables:** Consent/anonymization notes, gold dataset split, scoring script, regression report theo module/model/prompt và end-to-end evidence.
 480 - **Dependencies:** LLM-03 đến LLM-08; cần provider thật, normalized transcript và Web persistence cho full live path.
 481 - **Affected components:** tests/fixtures/, evaluation tooling, docs/report generated sau khi chạy.
 482 - **Implementation approach:** Đo precision/recall/F1 từng module, owner/deadline, evidence entailment, hallucination, temporal state và empty/contradictory cases; nhóm chốt threshold sau baseline.
 483 - **Acceptance Criteria:** Kết quả lưu config, dataset version, số lần retry/latency; tách fixture/mock khỏi provider thật; không ghi threshold chưa duyệt.
 484 - **Testing strategy:** Offline regression trên holdout fixtures; P11-05 live provider acceptance trên audio/transcript có quyền sử dụng.
 485 - **Priority / complexity:** P1 / M.
 486 - **Roadmap mapping:** P07-06, P11-01 và P11-05.

 498 ## 11. Architecture Decisions và trade-offs
 499 
 500 | Quyết định | Trạng thái | Lựa chọn/Trade-off |
 501 |---|---|---|
 502 | Python/FastAPI hay TypeScript/NestJS | **Proposed decision** | Dùng Python 3.12+, FastAPI, Pydantic v2 theo baseline: schema validation/AI adapter dễ cô lập; đổi lại repo thêm runtime/toolchain ngoài Next/Nest/pnpm. Không xem đây là stack đã có trong repo. |
 503 | REST hay message queue giữa Web và LLM | **Confirmed requirement** | REST/JSON đồng bộ tại boundary; Web job chạy background. Đơn giản, dễ contract-test; request dài cần timeout budget phù hợp. Queue riêng ở LLM không cần trong MVP. |
 504 | Stateless hay stateful LLM Service | **Confirmed requirement** | Stateless, không DB/job store; Web sở hữu dedupe, job state và persistence. Điều này scale đơn giản nhưng retry sau timeout có thể gọi provider lần nữa. |
 505 | Single-pass hay multi-stage extraction | **Proposed decision** | Một generation cho tất cả module được yêu cầu trong một window, deterministic temporal, batched evidence verifier và tối đa một schema repair. Cân bằng cost/latency với correctness; benchmark mới quyết định tách stage/module. |
 506 | LLM-only hay hybrid temporal resolution | **Proposed decision theo yêu cầu thiết kế** | LLM phát hiện phrase/context; Python calendar rules tính ngày/range. Tính deterministic và test được; phrase tự nhiên mơ hồ vẫn phải needs_review. |
 507 | Synchronous request hay asynchronous worker API | **Confirmed requirement** | POST /v1/extractions giữ HTTP đến khi xong; Web quản lý background job. Không tạo 202, polling hoặc queue ở LLM Service. |
 508 | Provider-specific hay provider-agnostic | **Confirmed requirement** | Contract provider-neutral và có adapter/configurable provider; MVP chỉ triển khai một adapter thật sau P00. Trade-off là interface nhỏ cần map capability/token/error khác nhau. |
 509 | Bearer token và private networking | **Proposed decision** | Token service-to-service + private network là baseline nhẹ; cần nhóm chốt secret distribution, TLS termination, rotation và môi trường local. |
 510 | Evidence verifier pass | **Proposed decision** | Một batch verification riêng cho semantic entailment; tăng token/latency nhưng đáp ứng yêu cầu source grounding. Có thể thay đổi sau evaluation, không được coi ID hợp lệ là đủ. |
 511 | Windowing transcript dài | **Proposed MVP decision** | Segment-aligned window + bounded overlap/dedup; giữ evidence mà không thêm queue/vector store. Map-reduce phức tạp chỉ sau benchmark. |

  36 ## 2. HTTP API
  37 
  38 ### 2.1 Endpoint
  39 
  40 Các endpoint dưới đây thuộc LLM Service. Chúng có base URL và process riêng với NestJS API, dù cùng dùng đường dẫn `/health`.
  41 
  42 | Method | Path | Mục đích | Thành công |
  43 |---|---|---|---|
  44 | GET | `/health` | Kiểm tra process và cấu hình cơ bản; không gọi provider | `200 OK` |
  45 | POST | `/v1/extractions` | Trích xuất đồng bộ các module được yêu cầu | `200 OK` |
  46 | GET | `/openapi.json` | OpenAPI schema do FastAPI sinh từ Pydantic models | `200 OK` |
  47 
  48 `GET /health` của LLM Service không phải bằng chứng provider đang hoạt động; endpoint không gửi request thử tới LLM provider. API Nest hiện cũng có `GET /health` nhưng trả `{"status":"ok","service":"api"}` và chỉ dành cho service đó.
  49 
  50 Response health đề xuất:
  51 
  52 ~~~json
  53 {
  54   "status": "ok",
  55   "service": "llm-service",
  56   "contract_version": "1.0"
  57 }
  58 ~~~
  59 
  60 ### 2.2 HTTP semantics và content
  61 
  62 - Request và response sử dụng UTF-8 JSON.
  63 - `POST /v1/extractions` yêu cầu `Content-Type: application/json`; client nên gửi `Accept: application/json`.
  64 - Request xử lý đồng bộ tại ranh giới service: giữ kết nối HTTP cho đến khi mọi module được yêu cầu hoàn tất hoặc request thất bại.
  65 - Thành công chỉ trả `200`; service không tạo job, queue, database record hay endpoint polling riêng. Web Backend tạo job và gọi LLM Service trong background job của Web.
  66 - Request chỉ thành công nếu mọi module trong `requested_modules` có kết quả hợp lệ. Service không trả extraction thành công khi một module được yêu cầu bị lỗi.
  67 - `GET /openapi.json` phản ánh schema đang triển khai. Schema này phải được kiểm tra trong contract tests trước khi Web Backend tích hợp.
  68 
  69 ### 2.3 Versioning
  70 
  71 - Path `/v1` xác định major API version.
  72 - `contract_version` trong body phải bằng `"1.0"` ở contract này. Trường giúp phát hiện fixture/client không tương thích; nó không thay thế version trong path.
  73 - Thêm field optional hoặc enum value tương thích có thể giữ `/v1`, sau khi cập nhật OpenAPI và contract tests.
  74 - Đổi kiểu field, đổi ý nghĩa `null`, hoặc đổi cách xác định module là breaking change: tạo `/v2`, không âm thầm thay đổi `/v1`.
  75 - `requested_modules` phải liệt kê rõ module; không có giá trị `all` hoặc mặc định ngầm.
  76 
  77 ### 2.4 Authentication giữa service
  78 
  79 Đề xuất dùng bearer token riêng giữa Web Backend và LLM Service:
  80 
  81 ~~~http
  82 Authorization: Bearer <LLM_SERVICE_TOKEN>
  83 ~~~
  84 
  85 Token phải được cấp từ secret store/environment của deployment, so sánh an toàn, có quy trình rotate và không được ghi log. Production chỉ expose LLM Service trên network nội bộ có TLS tại boundary phù hợp; không public endpoint trích xuất trực tiếp. `GET /health` có thể không yêu cầu token nhưng chỉ mở trong network nội bộ/health-check path.
  86 
  87 `401` nghĩa token thiếu hoặc sai; `403` nghĩa caller đã xác thực nhưng chưa được phép gọi. Đây là đề xuất; repository hiện chưa có service-to-service auth convention.
  88 
  89 ### 2.5 Timeout, retry và idempotency
  90 
  91 Web Backend sở hữu lifecycle, retry và deduplication của job. LLM Service không giữ trạng thái giữa các request.
  92 
  93 - Deployment phải cấu hình `provider_timeout_seconds` và `request_timeout_seconds`. Request budget bao gồm mọi provider call, evidence verification và một lần structured-output repair nếu có.
  94 - Giá trị khởi đầu đề xuất, chưa phải SLA được phê duyệt: provider call tối đa 60 giây; toàn request tối đa 180 giây; HTTP client của Web chờ ít nhất 190 giây. Điều chỉnh bằng benchmark P11.
  95 - Khi budget hết, trả `504 PROVIDER_TIMEOUT` hoặc `504 REQUEST_TIMEOUT`; không trả extraction một phần dưới dạng thành công.
  96 - Khi provider rate-limit, ánh xạ thành `503 PROVIDER_RATE_LIMIT`, kèm `Retry-After` nếu provider có thông tin an toàn để chuyển tiếp.
  97 - Web chỉ retry lỗi transient được đánh dấu `retryable: true`, dùng exponential backoff có jitter, giới hạn theo job policy và tôn trọng `Retry-After`. Không retry lỗi input, version, payload hay evidence không an toàn.
  98 - `request_id` do Web tạo và giữ nguyên qua các lần retry của cùng một logical extraction. Đây là correlation identifier, không phải idempotency key.
  99 - Vì LLM Service stateless, gửi lại cùng `request_id` vẫn có thể gọi provider và phát sinh chi phí lần nữa. Web phải dedupe job theo tối thiểu `meeting.id`, `transcript.revision_id`, module set và extraction config; không chạy đồng thời hai job giống nhau; không ghi kết quả trùng sau khi đã hoàn tất.
 100 - Nếu HTTP timeout xảy ra sau khi provider đã xử lý nhưng trước khi client nhận response, kết quả lần gọi đó không thể tra lại ở LLM Service. Web có thể retry trong job policy nhưng phải chấp nhận khả năng provider xử lý hai lần.
 101 
 102 ### 2.6 Giới hạn request và transcript dài
 103 
 104 - Giới hạn byte của body phải cấu hình theo deployment và được công bố trong mô tả OpenAPI. Vượt ngưỡng trả `413 PAYLOAD_TOO_LARGE`; client không retry nguyên payload.
 105 - Transcript được kiểm tra token budget trước khi gọi provider. Transcript vượt context window phải được chia theo segment boundaries và tổng hợp theo chiến lược ở [Architecture](./llm-service-architecture.md#16-chiến-lược-transcript-dài).
 106 - Nếu transcript vượt giới hạn body hoặc giới hạn xử lý đã cấu hình, hoặc không thể xử lý trong request budget sau khi chia cửa sổ, trả `413 TRANSCRIPT_TOO_LONG`. Không cắt bỏ transcript âm thầm và không retry payload nguyên trạng.
 107 - Không có giới hạn token cố định trong contract vì model/provider chưa được nhóm chọn. Provider adapter phải cung cấp context limit; deployment phải cấu hình hard limit trước khi nhận traffic.
 108 - Client không tự chia transcript thành các request độc lập để thay cho LLM Service: cách đó có thể làm mất deduplication, ngữ cảnh toàn cuộc họp và tính nhất quán temporal.

 239 | `segments[].id` | string | Có | ID duy nhất trong revision, 1–128 ký tự; giữ nguyên khi trích xuất. |
 240 | `segments[].start` | number | Có | Số giây tính từ đầu audio gốc, finite và `>= 0`. |
 241 | `segments[].end` | number | Có | Số giây tính từ đầu audio gốc, finite, lớn hơn `start` và `<= duration_seconds`. |
 242 | `segments[].speaker_id` | string hoặc null | Có | ID opaque do Audio Processing Service cấp, ổn định trong transcript revision; `null` nghĩa chưa biết/không gán được. Không đồng nghĩa với danh tính participant. |
 243 | `segments[].text` | string | Có | Nội dung transcript đã normalize, trim và không rỗng. Đây là text evidence; giữ nguyên ý và không gửi ASR provider payload/raw audio. |
 244 
 245 Timestamp là giây dạng số thực trên audio gốc sau khi Audio Processing Service đã cộng offset khi stitch các chunk. Segment phải được gửi theo `start` không giảm dần. Segment overlap được chấp nhận vì hai speaker có thể nói đồng thời; overlap tự nó không phải validation error. Segment ID trùng, thời gian âm, `end <= start`, `end` vượt duration hoặc thứ tự không hợp lệ trả `400 VALIDATION_ERROR`.
 246 
 247 Speaker thiếu được biểu diễn bằng `speaker_id: null`; không được tự tạo speaker hoặc gán participant dựa trên suy đoán ngôn ngữ. Speaker chưa map nhưng có ID vẫn hợp lệ. Nếu `speaker_id` có mapping trong participant, đó là mapping do Web Backend/Audio Processing Service xác nhận, không phải suy luận của LLM.

 258 ### 3.3 Quy tắc validation tổng quát
 259 
 260 - Field không được khai báo trong contract bị từ chối để tránh typo âm thầm; thay đổi tương thích phải đi kèm version/schema update.
 261 - `request_id`, meeting ID, revision ID, participant ID và segment ID không được rỗng hoặc trùng trong phạm vi được quy định.
 262 - `speaker_id` có thể null; segment text không thể null.
 263 - Timestamps luôn thuộc bản ghi âm gốc, không phải thời gian tương đối trong audio chunk.
 264 - Request hợp lệ không bảo đảm nội dung extraction thành công; provider, structured output và evidence được xử lý riêng theo error contract.
 265 - Không nhận audio bytes, file path, diarization raw response, provider-specific ASR JSON hoặc database IDs của artifact trong request.

 278   "meeting_id": "meeting-42",

 280   "requested_modules": [
 281     "meeting_summary",
 282     "action_items",

 284     "open_issues",
 285     "follow_up_items",
 286     "timeline_events"
 287   ],
 288   "modules": {
 289     "meeting_summary": {},
 290     "action_items": [],
 291     "decision_log": [],
 292     "open_issues": [],

 297     "provider": "example-provider",

 311 Trong schema thực, object `meeting_summary` phải có đầy đủ field theo mục 5; `{}` ở đây chỉ minh họa vị trí module.
 312 
 313 | Field | Type | Bắt buộc | Ý nghĩa |
 314 |---|---|---:|---|
 315 | `contract_version` | string | Có | `"1.0"`. |
 316 | `request_id` | string | Có | Echo đúng ID trong request. |
 317 | `status` | string | Có | Với HTTP 200 luôn bằng `"completed"`; không có `"partial"` hoặc `"failed"` trong success body. |
 318 | `meeting_id` | string | Có | Echo `meeting.id`. |
 319 | `transcript_revision_id` | string | Có | Echo đúng revision đã trích xuất. |
 320 | `requested_modules` | string array | Có | Echo đúng tập module của request, giữ thứ tự request. |
 321 | `modules` | object | Có | Luôn có đủ sáu key module; semantics theo mục 4.2. |
 322 | `processing` | object | Có | Metadata giúp tái lập extraction; không chứa prompt bí mật, transcript hoặc chain-of-thought. |
 323 
 324 `processing.provider`, `model_id`, `prompt_version` và `evidence_prompt_version` là bắt buộc. Verifier prompt version không thể null trong response thành công vì semantic evidence verification thuộc contract. Timestamp RFC 3339 UTC. `token_usage` là object hoặc null nếu provider không trả usage; nếu có, hai giá trị token phải là số nguyên không âm.
 325 
 326 ### 4.2 Module state, empty và null
 327 
 328 | Giá trị | Ý nghĩa |
 329 |---|---|
 330 | List `[]` | Module đã được yêu cầu, chạy thành công, nhưng không tìm thấy item phù hợp. Đây là kết quả rỗng hợp lệ. |
 331 | List có item | Module đã chạy; mỗi item phải thỏa schema và source-grounding rules. Item còn bất định có `needs_review: true`. |
 332 | `null` | Module chưa chạy hoặc không có kết quả dùng được. Trong response thành công, chỉ module không có trong `requested_modules` mới được null; nếu module được yêu cầu nhưng không có kết quả dùng được, toàn request phải trả non-2xx error envelope. `requested_modules` phân biệt module không chạy với processing failure. |
 333 | Processing failure | Không trả HTTP 200. Trả error envelope; không biểu diễn module lỗi bằng `[]` hoặc coi `null` là extraction thành công. |
 334 
 335 Nếu module được yêu cầu nhưng không sinh được kết quả có thể dùng theo contract, toàn request thất bại bằng error code phù hợp. Không được trả `null` cho requested module trong response `status: "completed"`. `needs_review: true` dùng cho artifact có nội dung và evidence có thể dẫn tới nguồn nhưng cần người xác nhận; nó không thay thế processing failure khi output sai schema hoặc không có evidence hợp lệ.
 336 
 337 ### 4.3 Processing IDs và thứ tự
 338 
 339 - `ACT-001`, `DEC-001`, `ISS-001`, `FLW-001`, `EVT-001` là ID hiển thị trong một response; service gán sau validation, không để model tự chọn ID.
 340 - ID được gán sau khi sort từng module và đánh số liên tục theo đúng thứ tự item được trả về; đây không phải durable database ID. Web Backend tạo/persist ID riêng.
 341 - `source_timestamp` là projection để hiển thị; được tính từ `start` nhỏ nhất trong `source_segment_ids` của item, format `HH:MM:SS.mmm`. Không dùng timestamp do model tự trả.
 342 - `source_segment_ids` là định danh evidence ổn định hơn timestamp; client nên dùng ID để tìm segment rồi seek audio bằng `segments[].start`.
 343 - Các list ngoài Timeline Events được xếp theo source time tăng dần. Timeline Events được xếp theo resolved date/range start, sau đó theo source time; item chưa resolve nằm sau item có ngày và được gắn review.

 593 ### 5.7 TemporalResolution dùng chung
 594 
 595 `TemporalResolution` là proposed extension dùng trong Action Items, Follow-ups và Timeline Events. Field raw được giữ ở module cha: `raw_due_expression`, `target_trigger_or_date` hoặc `raw_statement`.
 596 
 597 | Field | Type | Bắt buộc | Ý nghĩa |
 598 |---|---|---:|---|
 599 | `status` | string | Có | Một trong `exact_date`, `date_range`, `unresolved`. |
 600 | `resolved_date` | date string hoặc null | Có | Ngày exact theo `YYYY-MM-DD`, chỉ có với `exact_date`. |
 601 | `start_date` | date string hoặc null | Có | Đầu khoảng bao gồm cả ngày bắt đầu, chỉ có với `date_range`. |
 602 | `end_date` | date string hoặc null | Có | Cuối khoảng bao gồm cả ngày kết thúc, chỉ có với `date_range`. |
 603 | `needs_review` | boolean | Có | false chỉ khi ngày exact đã được resolve rõ; true với range/unresolved để UI không trình bày thành deadline giả. |
 604 | `source_segment_ids` | string array | Có | Evidence của biểu thức thời gian; là subset của source IDs ở artifact. |
 605 
 606 Invariant:
 607 
 608 - `exact_date`: `resolved_date` có giá trị; `start_date` và `end_date` null; `needs_review` false.
 609 - `date_range`: `resolved_date` null; cả `start_date` và `end_date` có giá trị, `start_date <= end_date`; `needs_review` true.
 610 - `unresolved`: tất cả ngày null; `needs_review` true.
 611 - Nếu không có biểu thức thời gian, resolution object null; không tạo object `unresolved` thay cho việc không có deadline.
 612 - `due_date` bằng `due_date_resolution.resolved_date` chỉ ở trạng thái exact; các trạng thái khác là null.
 613 - IDs temporal là evidence subset, không được tạo từ segment ngoài request.
 614 
 615 ### 5.8 Quy tắc chung cho mọi module
 616 
 617 - Không tự bịa owner, due date, priority, rationale, alternatives, blocker severity hoặc danh tính speaker.
 618 - Không đổi proposal/opinion thành decision; không đổi Open Issue thành Action Item nếu không có commitment; không đổi Follow-up thành task chỉ vì có động từ.
 619 - Không đặt claim không có evidence vào field bình thường rồi chỉ dựa vào một confidence score. Nếu claim còn hữu ích nhưng chưa thể xác minh, gắn `needs_review: true`; nếu không có source ID hợp lệ thì bỏ claim hoặc trả processing error khi module không còn kết quả dùng được.
 620 - `needs_review` phải bằng true khi `review_reasons` không rỗng; khi false, `review_reasons` phải là `[]`.
 621 - Với array module, không có item phù hợp là `[]`, không phải null. Summary vẫn là object nếu được yêu cầu; metadata đã biết được copy/tính từ request.
 622 - Các danh sách artifact ngoài Timeline Events được sort theo `source_timestamp` tăng dần. Timeline Events được sort theo ngày exact hoặc ngày bắt đầu của range, sau đó theo `source_timestamp`; item unresolved đứng sau item có ngày. ID do service gán tuần tự theo thứ tự trả về của từng module.
 623 - `review_reasons` chỉ nhận các mã: `owner_unconfirmed`, `date_range_needs_confirmation`, `temporal_unresolved`, `evidence_unverified`, `conflicting_statements`, `speaker_unmapped` và `claim_uncertain`. Dùng mảng rỗng khi không cần review; client nên xử lý mã chưa biết theo hướng tương thích khi contract được mở rộng.

 625 ## 6. Temporal resolution
 626 
 627 ### 6.1 Nguồn ngày và timezone
 628 
 629 - Chỉ dùng `meeting.anchor_date` làm ngày tham chiếu; tuyệt đối không dùng ngày hiện tại của server, container hoặc provider.
 630 - `anchor_date` là ngày dân sự địa phương của cuộc họp, không có giờ.
 631 - Calendar arithmetic thực hiện trên ngày địa phương theo `meeting.timezone` (IANA). Không đổi timezone của transcript timestamps; chúng là số giây từ đầu audio.
 632 - `timezone` bắt buộc để diễn giải mốc ngày/giờ và đổi sang datetime ở lớp khác. v1 chỉ trả ngày; không tự tạo giờ trong ngày khi transcript không nêu.
 633 - Nếu timezone không hợp lệ hoặc thiếu anchor date, request bị từ chối trước LLM.
 634 
 635 ### 6.2 Quy tắc resolve v1
 636 
 637 | Biểu thức | Quy tắc |
 638 |---|---|
 639 | Ngày ISO hoặc ngày cụ thể có đủ ngày/tháng/năm | Parse nguyên văn; kiểm tra ngày lịch hợp lệ; trả `exact_date`. |
 640 | “Thứ Sáu này” | Ngày thứ Sáu đầu tiên từ anchor date trở đi trong lịch địa phương; nếu anchor đã là thứ Sáu thì là cùng ngày. Với anchor `2026-10-05`, kết quả `2026-10-09`. |
 641 | “Tuần sau” | Khoảng từ thứ Hai đến Chủ nhật của ISO week kế tiếp, inclusive. Với anchor `2026-10-05`, khoảng `2026-10-12` đến `2026-10-18`; không gán thành thứ Hai. |
 642 | “Tuần này” | Khoảng thứ Hai–Chủ nhật chứa anchor date. |
 643 | “Cuối tháng” | Ngày cuối cùng của tháng chứa anchor date; “cuối tháng sau” là ngày cuối tháng kế tiếp. Với anchor `2026-10-05`, ngày là `2026-10-31`. Đây là policy đề xuất dựa trên ví dụ trong tài liệu gốc. |
 644 | “Ngày 12” không có tháng/năm | Resolve chỉ khi ngữ cảnh transcript xác định duy nhất tháng/năm; nếu không, `unresolved`. Không dùng ngày hệ thống để chọn năm. |
 645 | Mốc thời gian mâu thuẫn hoặc không đủ thông tin | Giữ raw phrase, trả `unresolved`, tất cả date field null và `needs_review: true`. |
 646 | Ngày không tồn tại, ví dụ 30/02 | Không tự sửa; trả `unresolved` hoặc lỗi output nếu model đã tạo date không hợp lệ. |
 647 
 648 `date_range` biểu thị đúng độ chính xác của câu nói; không được ép thành exact date để tiện sắp lịch. Range/unresolved luôn `needs_review: true` trong v1 để UI thể hiện rõ ngày chưa được chốt.
 649 
 650 ### 6.3 Nhất quán giữa modules
 651 
 652 LLM chỉ trích raw phrase, event/task context và source segment IDs. Python `TemporalResolver` tính calendar result. Cùng một expression trong Action Item, Follow-up và Timeline phải dùng cùng hàm resolve và cùng anchor/timezone; không để mỗi prompt tự tính một ngày khác.
 653 
 654 Với dữ liệu mẫu `anchor_date = 2026-10-05`, `timezone = Asia/Ho_Chi_Minh`:
 655 
 656 ~~~json
 657 {
 658   "status": "date_range",
 659   "resolved_date": null,
 660   "start_date": "2026-10-12",
 661   "end_date": "2026-10-18",
 662   "needs_review": true,
 663   "source_segment_ids": ["seg-003"]
 664 }
 665 ~~~
 666 
 667 Các test lịch phải có cuối tháng 2 ở năm nhuận/không nhuận, đổi tháng/năm, anchor vào đúng weekday, timezone IANA hợp lệ, range qua năm và phrase thiếu ngữ cảnh. Không đặt quality threshold cho temporal accuracy trước khi nhóm có baseline.

 669 ## 7. Source grounding
 670 
 671 ### 7.1 Ràng buộc evidence
 672 
 673 - Artifact và từng key topic phải có `source_segment_ids` trỏ tới ID tồn tại trong `transcript.segments` của đúng request/revision.
 674 - ID trùng, ID không tồn tại hoặc reference sang meeting/revision khác là output không hợp lệ.
 675 - Mỗi source list không lặp ID; thứ tự theo `start` tăng dần. Temporal source IDs phải là subset evidence của artifact chứa nó.
 676 - `source_timestamp` được service tính bằng `min(segments[id].start)` rồi format `HH:MM:SS.mmm`; không chấp nhận timestamp do LLM tự tính.
 677 - ID tồn tại chỉ chứng minh reference hợp lệ về mặt cấu trúc, không chứng minh câu nói hỗ trợ claim về nghĩa.
 678 - Evidence verifier phải kiểm tra entailment giữa claim và text được trích dẫn. Nếu không hỗ trợ: loại claim, hoặc giữ item có `needs_review: true` và lý do `evidence_unverified` nếu phần còn lại vẫn hữu ích. Nếu module không còn output dùng được, trả `502 UNVERIFIED_EVIDENCE`, không trả empty list để giả như không tìm thấy item.
 679 - Speaker identity chỉ được đưa thành participant name khi participant-speaker mapping có trong request hoặc transcript nêu rõ; `speaker_id` đơn thuần là nhãn kỹ thuật.
 680 - Không suy luận owner, priority, deadline, rationale hoặc identity từ ngữ cảnh chung nếu source không nói.
 681 
 682 ### 7.2 Click-to-play
 683 
 684 Web Backend lưu nguyên segments theo transcript revision. UI nhận `source_segment_ids`, tìm segment tương ứng trong đúng revision, rồi seek audio gốc tới `segments[].start`. Không seek theo timestamp do model tự tạo, không dùng offset cục bộ chunk, không dùng ID từ meeting khác. Nếu revision hiện tại khác `transcript_revision_id` trong response, Web không được gắn evidence cũ vào transcript/audio mới.
 685 
 686 ## 8. Error contract
 687 
 688 Mọi lỗi dùng cùng envelope. `request_id` bằng ID đã parse được hoặc null nếu body không có ID hợp lệ; response nên lặp ID an toàn trong log/header correlation. `errors` chứa zero hoặc nhiều field issues; không trả raw provider body, API key, prompt nội bộ, transcript, stack trace hoặc SQL.
 689 
 690 ~~~json
 691 {
 692   "statusCode": 400,
 693   "code": "VALIDATION_ERROR",
 694   "message": "Yêu cầu trích xuất không hợp lệ.",
 695   "request_id": "req-invalid-01",
 696   "retryable": false,
 697   "retry_after_seconds": null,
 698   "errors": [
 699     {
 700       "path": "meeting.anchor_date",
 701       "code": "FIELD_REQUIRED",
 702       "message": "Trường này là bắt buộc."
 703     }
 704   ]
 705 }
 706 ~~~
 707 
 708 | HTTP | Error code | Khi nào | Retry policy |
 709 |---:|---|---|---|
 710 | 400 | `VALIDATION_ERROR` | JSON/schema/type, enum, timestamp, ID, timezone hoặc field constraint sai. | Không retry nguyên request; caller sửa input. |
 711 | 400 | `UNSUPPORTED_CONTRACT_VERSION` | `contract_version` không hỗ trợ. | Không retry; client phải dùng version được hỗ trợ. |
 712 | 401 | `AUTHENTICATION_REQUIRED` | Token thiếu/sai. | Không tự retry; sửa secret/config. |
 713 | 403 | `SERVICE_FORBIDDEN` | Caller hợp lệ nhưng không được phép. | Không retry. |
 714 | 413 | `PAYLOAD_TOO_LARGE` | Body vượt byte limit deployment. | Không retry payload nguyên; giảm/chia request theo hướng dẫn contract. |
 715 | 413 | `TRANSCRIPT_TOO_LONG` | Token/context/request budget vượt giới hạn sau chính sách windowing. | Không retry nguyên request; Web báo lỗi hoặc yêu cầu workflow xử lý lại theo policy. |
 716 | 422 | `EMPTY_TRANSCRIPT` | Không có segment hoặc tất cả text rỗng/whitespace; bao gồm transcript không có speech text dùng được. | Không retry; yêu cầu transcript hợp lệ. |
 717 | 429 | `CAPACITY_LIMIT` | LLM Service đang giới hạn concurrency/rate nội bộ. | Có thể retry sau `Retry-After`; exponential backoff có jitter và giới hạn job. |
 718 | 502 | `PROVIDER_FAILURE` | Provider lỗi hoặc trả lỗi không dùng được. | Retry chỉ khi error được phân loại transient; tối đa theo Web job policy. |
 719 | 502 | `INVALID_STRUCTURED_OUTPUT` | Provider không tạo output đúng schema sau tối đa một lần repair có giới hạn. | Mặc định không tự retry; retry một lần chỉ khi job policy cho phép và chấp nhận chi phí lặp. |
 720 | 502 | `UNVERIFIED_EVIDENCE` | Module được yêu cầu không còn claim nào dùng được sau evidence verification. | Không retry tự động; cần human review hoặc thay đổi prompt/model. |
 721 | 503 | `PROVIDER_RATE_LIMIT` | Provider rate-limit; không expose quota detail/headers nhạy cảm. | Retry khi có `Retry-After`, tối đa theo Web job policy. |
 722 | 503 | `PROVIDER_CONFIGURATION_ERROR` | Provider credential/config không hợp lệ hoặc thiếu. | Không retry cho đến khi cấu hình được sửa. |
 723 | 504 | `PROVIDER_TIMEOUT` | Provider call vượt giới hạn. | Có thể retry có giới hạn nếu job còn active; kết quả lần gọi có thể không biết nên có thể phát sinh chi phí lặp. |
 724 | 504 | `REQUEST_TIMEOUT` | Tổng request budget hết. | Retry có giới hạn theo Web job policy; không tự tạo background job tại LLM Service. |
 725 | 500 | `INTERNAL_ERROR` | Lỗi nội bộ không phân loại được. | Chỉ retry có giới hạn nếu server đánh dấu `retryable: true`; không gửi stack trace. |
 726 
 727 `retryable` và `retry_after_seconds` là phần mở rộng đề xuất để Web quyết định thống nhất; không thay cho HTTP status. Với lỗi provider không xác định được transient/permanent, mặc định `retryable: false`. LLM Service không trả `200` có status `failed`.

1192 ## 10. Contract test cases và acceptance criteria
1193 
1194 Contract tests không cần provider thật; dùng fixtures và fake provider để kiểm tra API/schema. Bộ integration với provider thật thuộc P11 và phải ghi rõ dữ liệu, model/config, chi phí và giới hạn.
1195 
1196 - `GET /health` trả đúng service name/version và không gọi provider.
1197 - `GET /openapi.json` thể hiện request, response và error schemas hiện tại.
1198 - Request đủ sáu module trả đủ sáu key, đúng schema, echo request/revision IDs.
1199 - Request Summary + Actions chỉ chạy hai module; bốn module còn lại null; empty result cho list module là `[]`.
1200 - Output có module requested null, thiếu source hoặc field sai phải không được trả `status: completed`.
1201 - `contract_version` không hỗ trợ, module enum sai/trùng, required field thiếu, timezone sai và unknown field trả `400`.
1202 - `segments: []`, text trắng hoặc không có text speech dùng được trả `422 EMPTY_TRANSCRIPT`.
1203 - `segment.id` trùng, timestamp âm, `end <= start`, segment ngoài duration, hoặc start đảo thứ tự trả `400`.
1204 - Overlap hợp lệ giữa hai segment được nhận; `speaker_id: null` được nhận và không bị tự gán.
1205 - Participant-speaker mapping trùng một speaker sang hai người bị từ chối.
1206 - Byte limit trả `413 PAYLOAD_TOO_LARGE`; transcript vượt token budget sau windowing trả `413 TRANSCRIPT_TOO_LONG`.
1207 - `anchor_date=2026-10-05`: “thứ Sáu này” → `2026-10-09`; “tuần sau” → `2026-10-12` đến `2026-10-18`; “cuối tháng” → `2026-10-31`.
1208 - Ngày tháng/năm, năm nhuận, timezone địa phương và biểu thức mơ hồ được test; không test nào phụ thuộc ngày hệ thống.
1209 - Exact temporal state có đúng một `resolved_date`; range có đủ hai đầu và không có `resolved_date`; unresolved không có ngày.
1210 - `source_segment_ids` không tồn tại/khác revision, source timestamp không khớp segment start hoặc evidence verifier bác claim phải bị loại, đánh review hoặc trả structured failure theo quy tắc.
1211 - `needs_review` phải nhất quán với `review_reasons`; provider không được ghi stack trace/API key vào envelope.
1212 - Provider timeout/rate-limit/structured output lỗi ánh xạ đúng status, code, retry flag và `Retry-After`; không trả 200 một phần.
1213 - Retry giữ `request_id`; test Web Backend chứng minh dedupe theo meeting/revision/module/config thay vì dựa vào LLM Service.
1214 - Full JSON examples trong tài liệu phải parse được bằng JSON parser và khớp field tables.
1215 
1216 Acceptance cho contract v1: ba service có thể xây fixture tương thích; mọi artifact có source IDs kiểm tra được; relative date giữ đúng độ chính xác; module chưa yêu cầu có null, module chạy không có item có []; processing failure luôn là non-2xx error envelope.

P00 phải kiểm tra quyền sử dụng thực tế và thời hạn dự án; nếu cần đổi provider, nhóm cập nhật yêu cầu trước, giữ hợp đồng timestamp và speaker. Chưa coi quyền truy cập API là đã xác minh. Nguồn: [Speech-to-text — Timestamps](https://developers.openai.com/api/docs/guides/speech-to-text#timestamps).
  38 - **File lớn:** giới hạn hiện tại là 25 MB/request; kiểm tra dung lượng **file chunk sau encode**, không chỉ số phút. Giới hạn upload của ứng dụng cần cho phép file lớn hơn để đi qua chunking. Nguồn: [Speech-to-text — Longer inputs](https://developers.openai.com/api/docs/guides/speech-to-text#longer-inputs).
  39 - **Speaker:** phải có bước suy luận nhãn người nói từ audio hoặc phương án attribution được nhóm chấp thuận. `unknown` và sửa nhãn là fallback; chỉ gán tay không chứng minh tính năng tự động đã hoàn thành. Không dùng nội dung LLM suy đoán làm danh tính người nói đã xác thực.
  40 - **Export:** Markdown/copy summary là đầu ra rõ trong FC4; JSON là dữ liệu cấu trúc và có thể cho tải thêm. Product description còn nhắc HTML/PDF, nên P00 phải chốt có cần file HTML/PDF khi nghiệm thu. Nếu cần, bổ sung task P10; không tự bỏ yêu cầu hoặc mặc định đã có PDF.
  41 - **Ngày tháng:** với `anchor_date=2026-10-05`, “thứ Sáu này” là **2026-10-09**; `2026-10-08` là thứ Năm. “Tuần sau” chỉ xác định tuần nếu chưa có ngày cụ thể: giữ khoảng ngày/`needs_review`, không tự tạo deadline thứ Hai. P00 đồng bộ các ví dụ sai trong tài liệu gốc.
  42 
  43 **Phần bổ sung, cần phân biệt với yêu cầu gốc:** sửa transcript/biên bản và cảnh báo khi tạo lại là cải thiện hữu ích, đặt tại P10. Audit history đầy đủ, xử lý xung đột nhiều người sửa và phân quyền phức tạp là phần mở rộng, không chặn MVP khi nhóm chưa đưa vào yêu cầu.
  44 
  45 **Ngoài MVP theo đề tài:** live streaming transcription, bot tham gia Zoom/Meet/Teams, đồng bộ Calendar/Jira/Trello và voiceprint training.
  46 
  47 ## 3. Ghi chú triển khai tối thiểu
  48 
  49 Luồng chính: **Meeting + audio → kiểm tra/chia audio → Whisper transcript → speaker attribution → LLM trích xuất + xử lý ngày → giao diện + export**.
  50 
  51 - React/TypeScript và FastAPI/Pydantic là **stack đề xuất**, chưa phải ràng buộc từ đề tài. Chốt trong P00, không biến lựa chọn công cụ thành tính năng sản phẩm.
  52 - Dùng database và lưu audio trên local volume cho bản dev. Chỉ tạo model, endpoint và thư mục khi có task sử dụng; chưa cần nhiều lớp abstraction để dự phòng.
  53 - P03 xử lý nền có trạng thái để HTTP trả về sớm. P05 bổ sung độ bền khi restart/retry; cân nhắc Redis/RQ nếu cần queue riêng, chưa bắt buộc dựng từ P01.
  54 - Dữ liệu tối thiểu: meeting, participants, audio, job, transcript segments/words, speakers và sáu loại artifacts. Artifact tham chiếu segment trong cùng meeting; các field chi tiết bám schema tài liệu gốc.
  55 - Thiếu owner/deadline/rationale thì để `null` hoặc đánh dấu cần xác nhận; không tự bịa. JSON hợp lệ chưa đồng nghĩa nội dung đúng.
  56 - API key và audio riêng tư không đưa vào Git; fixture phải có quyền sử dụng. Bản deploy công khai cần bảo vệ quyền truy cập meeting/audio phù hợp.

  10 ## 1. Product Overview & Vision
  11 
  12 ### 1.1 Executive Summary
  13 
  14 The **Meeting Minutes Assistant** is an intelligent meeting productivity tool designed to convert raw meeting audio recordings into structured, accurate, and actionable meeting documentation.
  15 
  16 By leveraging speech-to-text (OpenAI Whisper API), speaker diarization/labeling, and LLM-driven business extraction, the product eliminates manual note-taking friction, preserves critical organizational memory, and ensures transparent team alignment.
  17 
  18 ### 1.2 Core Problem Statement
  19 
  20 - **Information Loss:** Crucial decisions, upcoming milestone commitments, and assigned deliverables discussed verbally are frequently forgotten.
  21 - **Distracted Attendees:** Meeting participants spend time taking fragmented notes instead of actively engaging in the discussion.
  22 - **Ambiguous Ownership:** Teams often leave meetings without a crisp, shared understanding of _who_ is responsible for _what_, and _when_ it is due.
  23 - **Vague Timelines:** Verbal scheduling commitments (e.g., _"Thứ 6 demo"_, _"Tuần sau deploy"_) are rarely converted into concrete calendar dates, causing slipped deadlines.
  24 - **Lack of Verifiable Context:** Traditional meeting summaries lack exact timestamps, making it difficult to trace why or when a decision was made.
  25 
  26 ### 1.3 Value Proposition
  27 
  28 - **Hands-Free Capture:** Record meetings directly in the browser/client or upload pre-recorded audio files.
  29 - **Verifiable Transcript:** Speaker-labeled transcripts with timestamps allow users to inspect the exact spoken source.
  30 - **High-Signal Business Artifacts:** Automated extraction of 6 core business modules:
  31     1. Meeting Summary
  32     2. Action Items
  33     3. Decision Log
  34     4. Open Issues / Unresolved Questions
  35     5. Follow-up Items
  36     6. Timeline / Event Extraction (Temporal Resolution to concrete dates)
  37

  53     - Extraction and formatting of all 6 defined business modules.
  54     - Temporal date resolution (converting relative statements like _"thứ 6 demo"_ to exact dates based on the meeting anchor date).

  61 - Automated direct integration with project management tools (e.g., auto-creating Jira tickets or Trello cards).

  89 ## 4. Deep Dive: Core Business Modules Covered
  90 
  91 To avoid ambiguity, ensure consistent extraction, and provide high utility, the MVP covers six business modules. Each module has a distinct definition, purpose, schema, and extraction boundary.
  92 
  93 ---
  94 
  95 ### Module 1: Meeting Summary
  96 
  97 - **Purpose:** Provide an executive-level overview of the meeting so team members or absent stakeholders can grasp the core discussions and outcomes in under 2 minutes.
  98 - **Key Components:**
  99     - **Meeting Context:** Title, Date, Duration, Participant list.
 100     - **Executive Overview:** 2–3 concise paragraphs summarizing the primary themes and outcomes.
 101     - **Core Discussion Pillars:** Bullet points highlighting the central topics debated or presented.
 102 - **Output Schema:**
 103     ```json
 104     {
 105         "title": "String",
 106         "date": "YYYY-MM-DD",
 107         "duration_minutes": "Number",
 108         "participants": ["String"],
 109         "overview": "String",
 110         "key_topics": [
 111             {
 112                 "topic": "String",
 113                 "brief_discussion": "String"
 114             }
 115         ]
 116     }
 117     ```
 118 
 119 ---
 120 
 121 ### Module 2: Action Items
 122 
 123 - **Purpose:** Capture clear, assignable, and accountable operational tasks committed during the meeting.
 124 - **Criteria:** Must be a specific task, have an identifiable owner (or role), and have a clear expected deliverable (with deadline if mentioned).
 125 - **Extraction Rules:**
 126     - If a person verbally commits (_"I will write the API spec by Friday"_), it is an Action Item.
 127     - Must reference the timestamp where the commitment was stated.
 128 - **Output Schema:**
 129     ```json
 130     [
 131         {
 132             "id": "ACT-001",
 133             "task": "Draft OpenAPI specification for meeting ingestion endpoint",
 134             "owner": "Alex",
 135             "due_date": "2026-10-10 or null",
 136             "priority": "High | Medium | Low",
 137             "source_timestamp": "00:14:22",
 138             "context": "Follows the discussion regarding audio payload limits"
 139         }
 140     ]
 141     ```

 145 ### Module 3: Decision Log
 146 
 147 - **Purpose:** Record settled choices, architectural directions, or policy agreements so that decisions are not reopened without cause.
 148 - **Criteria:** A topic where consensus or an authoritative choice was made.
 149 - **Extraction Rules:**
 150     - Distinguish decisions from proposals or opinions. A decision requires explicit agreement or team consensus.
 151     - Capture the _rationale_ behind why this option was chosen over alternatives.
 152 - **Output Schema:**

 162     ]
 163     ```

 168 
 169 - **Purpose:** Track unresolved debates, unanswered questions, blockers, and uncertainties that require further investigation before a decision can be reached.

 172     - Must clearly articulate what information or clarification is missing.

 210 ### Module 6: Timeline / Event Extraction (Temporal Resolution)
 211 
 212 - **Purpose:** Extract all project milestones, event schedules, release dates, and deadlines discussed verbally in the meeting, and convert relative temporal expressions into **concrete calendar dates**.
 213 - **Scope Definition:**
 214     - This is **NOT** the chronological duration/runtime of the meeting audio (e.g. 00:00 - 05:00).
 215     - This is the **Project Timeline & Milestones** stated by participants during the meeting.

 217     - Takes the **Meeting Anchor Date** (e.g., `05/10/2026`).
 218     - Identifies relative spoken phrases:
 219         - _"Thứ 6 demo"_ -> calculates the coming Friday date (`09/10/2026` or `08/10/2026` based on calendar).
 220         - _"Tuần sau deploy"_ -> calculates the target date/week (`12/10/2026`).
 221         - _"Cuối tháng submit report"_ -> calculates the end-of-month date (`31/10/2026`).
 222 - **Output Format:**
 223     - Chronologically ordered sequence of milestones/events:
 224         - `05/10/2026` — Meeting (Anchor)
 225         - `08/10/2026` — Demo
 226         - `12/10/2026` — Deployment
 227 - **Output Schema:**
 228     ```json
 229     [

 232             "event": "Meeting (Anchor)",
 233             "resolved_date": "2026-10-05",

 235             "source_timestamp": "00:00:00"
 236         },

 239             "event": "Demo",
 240             "resolved_date": "2026-10-08",

 242             "source_timestamp": "00:19:40"
 243         },
 244         {
 245             "id": "EVT-002",
 246             "event": "Deployment",
 247             "resolved_date": "2026-10-12",
 248             "raw_statement": "Tuần sau deploy",

 269 ## 5. Technical Considerations & Alignment
 270 
 271 1. **OpenAI Whisper API:**
 272     - Uses Whisper (`/v1/audio/transcriptions` with `verbose_json`) for high-fidelity speech-to-text and segment-level timestamps.
 273     - _Diarization:_ Pair Whisper timestamps with a speaker attribution pipeline (e.g., PyAnnote diarization or LLM turn-based speaker attribution with participant metadata).
 274 2. **Temporal Resolution Engine:**
 275     - Prompts provide the current meeting date (`anchor_date`) to the LLM.
 276     - The LLM applies temporal parsing rules (ISO 8601 date resolution) for Vietnamese and English expressions (e.g., _"thứ 6 này"_, _"tuần sau"_, _"cuối tháng"_, _"next Tuesday"_).
 277 3. **File Size & Chunking:**
 278     - OpenAI Whisper API has a 25 MB limit per request. Audio files exceeding this limit require pre-processing (chunking with slight overlap using `ffmpeg` or `pydub`).
 279 4. **Structured Document Output:**
 280     - Stores meeting artifacts in structured JSON and renders to clean, shareable Markdown and HTML/PDF exports.
