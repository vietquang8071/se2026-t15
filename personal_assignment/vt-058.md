# VT-058 — Best-Effort Extraction Completion Notification

**Project:** SE2026-T15 — AI-05 Meeting Minutes Assistant  
**Component:** `apps/llm-service`  
**Reference branch:** `feature/llm-03-provider-integration`  
**Planned assignment branch:** `feature/vt-058-llm-notification`  
**Specification version:** 1.0 — Approved design decisions, pending implementation review

## 1. Problem Statement

The Meeting Minutes Assistant's LLM Service processes meeting transcripts and produces validated structured artifacts, including Meeting Summary and Action Items.

The service currently does not emit a completion notification after successful extraction.

The change introduces a best-effort `extraction.completed` business event. Notification failures must not invalidate or alter a successful extraction outcome.

The implementation must also be tested against large input payloads, timeout risks, and concurrent workloads.

## 2. Scope

**In scope**

- Generate an `extraction.completed` event only after successful, validated extraction.
- Use an injectable notification adapter with a testable implementation.
- Isolate notification exceptions and timeouts from the primary extraction operation.
- Preserve the existing `/v1/extractions` request and response contract.
- Test input-size boundaries, including an exact-limit case.
- Perform pairwise, mutation, concurrency and performance experiments.

**Out of scope**

- Email, SMS, push notification and browser UI.
- Redis, RabbitMQ, Kafka or a durable message queue.
- Database schema changes and transaction management.
- Guaranteed notification delivery after process restart.
- Exactly-once delivery across retries.
- Changes to LLM prompts, model selection or extraction business rules.

## 3. Acceptance Criteria

**AC-01 — Successful extraction notification**

Given a valid extraction request and a successful verified extraction, when processing completes, the service schedules or dispatches an `extraction.completed` event exactly once within that request's execution path.

**AC-02 — No false success notification**

Given a request that fails authentication, validation, provider processing, response validation, evidence verification or request timeout, the service must not emit an `extraction.completed` event.

**AC-03 — Failure isolation**

Given a successful extraction, when notification processing raises an exception or exceeds its configured timeout, the extraction's HTTP status and response body remain identical to those produced without the notification failure.

**AC-04 — Safe event contract**

The notification event includes only allowlisted metadata: `event_type`, `request_id`, `meeting_id`, and `status`. It must not include transcript content, bearer tokens, OpenRouter credentials or provider responses.

**AC-05 — Large-input boundary preservation**

Requests whose UTF-8 body size exceeds the configured maximum must receive the existing `413 PAYLOAD_TOO_LARGE` error. A structurally valid request at the exact size limit must not be rejected solely because of its size.

## 4. Critical Invariants

**I-01 — Primary operation isolation**

Notification failure must not modify a successfully validated extraction result.

**I-02 — No false completion**

A failed extraction must never generate an `extraction.completed` event.

**I-03 — Contract preservation**

Notification functionality must not introduce new required request fields or modify the successful extraction response schema.

## 5. Non-Functional Constraints

**NFR-01 — Reliability:** Notification failures are isolated and recorded through safe diagnostics. Notification timeouts must be bounded.

**NFR-02 — Performance:** Evaluate 200 concurrent tasks against a target p95 latency of at most 5.0 seconds, with the workload and measurement boundaries explicitly documented.

**NFR-03 — Security:** Never expose transcript contents or secrets through notification events or logs.

**NFR-04 — Maintainability:** Minimize the change surface and reuse existing dependency injection and test conventions.

## 6. Test Requirements

- At least 10 test cases covering unit, integration/API and relevant service-level end-to-end behavior.
- Pairwise/combinatorial test design with documented factors and coverage.
- At least two negative tests and one risk-related failure-path test.
- An exact-boundary regression test capable of detecting a `>` to `>=` mutation.
- At least two AI-generated weak or duplicate tests must be corrected or removed, with evidence.
- Failure-first Red → implementation patch → Green evidence.
- Coverage analysis, flaky-test review and a reproducible load experiment.

## 7. Architectural Limitations

The current LLM Service returns a structured extraction result but does not own the application's PostgreSQL transaction.

Tests within this vertical slice can demonstrate isolation of the extraction operation from notification failures. They cannot, by themselves, prove database transaction durability, reliable notification delivery after restart or exactly-once processing.

These limitations must be documented as residual risks.

## 8. Definition of Done

All five acceptance criteria have traceable tests and verified execution evidence. The mutation is detected, the original code is restored, performance results are documented honestly, and the final patch is independently reviewable without changing unrelated LLM behavior.
